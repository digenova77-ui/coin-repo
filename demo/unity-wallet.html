Coin addresses — defined

Approved definition — unactivated

Approved by David, October 4, 2026. Not yet activated — the definition is sealed, the chain is not.

Derived from the architecture's own conventions — SHA-256, domain separators, base32. No imported formats.

Format
u1 · 28 payload chars · 4 checksum chars
e1 · 28 payload chars · 4 checksum chars
Alphabet
a–z, 2–7 (lowercase base32, no padding)

Derivation

  1. Unity ID: u1 ‖ base32( SHA-256("dualis.unity-id.v1" ‖ device_pubkey) )[0:28] ‖ checksum — from the bind ceremony's device key.
  2. Coin address: e1 ‖ base32( SHA-256("dualis.efuse.addr.v1" ‖ unity_id_payload) )[0:28] ‖ checksum — derived from the Unity ID. The binding is recomputable by anyone holding the ID: shown, not claimed.
  3. Checksum: base32( SHA-256("dualis.check.v1" ‖ payload) )[0:4] — catches a wrong character on paste.

Validation

Prefix u1/e1 → 32 base32 chars → checksum recomputed. Fail any step and the true reason is stated — never a silent accept.

The locked address — the core cause

Scheme-level constant. Nothing up the sleeve — recompute SHA-256("dualis.efuse.lock.v1:core-cause") and check it yourself. One way in (donations); directed out only to cause-work. Not really a black hole — it goes to the core cause.
